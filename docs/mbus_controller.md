# MBUS controller contract

`nokia_mbus_device` owns MAD2 PUP offsets `0x18..0x1a`, byte timing, status
generation, RX/TX holding state, and FIQ2/FIQ3 outputs. It exposes a received
byte input and a transmitted byte callback. Products may attach an independently
configured terminal device; ordinary profiles have no terminal by default.

## Recovered firmware contract

The v6.00 initializer at `0x2aafb4` aligns with the v5.01 initializer at
`0x2a8040`. Both perform the same sequence: reset control through bit 7, clear
the low status conditions, initialize the byte register, then leave control at
`0x4c` in receive mode. A bounded one-second trace records ten accesses to
`0x18..0x1a` and no transmitted bytes in either ROM.

The v6.00 FIQ handler at `0x2b56cc` establishes the data-path predicates:

- status bit 4 with control bit 5 calls the TX step at `0x2aae2a`;
- status bit 5 with control bit 6 calls the RX state machine at `0x2aae76`;
- RX reads the byte from `0x1a` and acknowledges MAD2 FIQ2 (`0x04`); and
- the low three status bits feed an error/reset branch.

`make verify-mbus` checks the identical two-ROM initialization and the negative
result that ordinary boot has no MBUS counterparty. Its external-input fixture
presents byte `0xa5` only after receive mode is active. Firmware observes
status `0xe7`, reads the byte through its real RX handler, and acknowledges
FIQ2. The later incomplete-frame behavior is deliberately outside the
controller acceptance contract.

## External byte-event fixture

All handset input compositions expose `MBUS_RX` as a logical event port.
Lua uses `port:write(value, 0x1ff)`: bits0..7 are the received byte and
bit8 is a toggling fixture strobe, not a ninth wire-data bit. The callback
passes only the low byte into `nokia_mbus_device::receive_byte`; readiness,
occupancy, firmware reads and FIQ handling remain controller/firmware-owned.
The port is `IPT_OUTPUT` because MAME dispatches these writes immediately.
Positional `field:set_value` inputs are sampled at video cadence and can
coalesce serial bytes. No startup event is generated by configuration loading.

`verify-6210-mbus-byte-events` sends a checksum-valid frame containing
`a5 a5 ff ff 00 00 00` and requires every byte to be accepted
and read before the next event. The payload has no qualified service meaning.
The original 5ms, timer-disabled 14-byte fixture independently passed on 3210 v6.00 and v5.01 using
`tools/run_mame_isolated.py` with `tools/mbus_input_probe.lua` and a10s run.
This proves repeated values and sub-video-frame event delivery, not a
measured service-tool cadence or bit-level electrical behavior. An unexpected
first `a5` instead causes NPE-3 firmware to disable reception; do not force
it back on to make a byte-stream test pass. The legacy single-byte harness
fixture now uses the event port and still passes `verify-mbus`.

`verify-6210-mbus-version-ingress` is a bounded read-query hypothesis:
`1f0010d10005000100030001d8`, tool node10 to phone00, typeD1, sequence01,
zero whole-frame XOR. It derives from the reference service-tool envelope,
not the independently established node1d terminal protocol below. All13
bytes were accepted in the original timer-disabled run, without a reply.
The ingress checker retains its transport-only scope. Current fixtures use
1.1ms gaps: above one character time, below the existing MBUSTIM period.

### NPE-3 service timer and version response

Current composition: `npe3mbus` inherits the own-upload/runtime-HLE setup
and enables MBUSTIM. The ordinary `npe3hle` retains its established disabled
clock because the combined service/call/sleep acceptance below is unresolved.
This is an explicit research split, not a workaround claimed as fidelity.
Retire the split when those contracts compose in one passing machine.
Fresh containment checks: `tmp/npe3-mbus-separated-service` passes service
and storage control; `tmp/npe3-mbus-contained-state-call` passes complete
ordinary call restoration; `tmp/npe3-mbus-contained-wake-negative` preserves
the clock-enabled End-decode failure and its raw-contact/IRQ observations.

Own 6210 v5.56 MCU (SHA1 `3d9ea319503e78ec69b60d72cda23e461e118ea9`)
unmasks FIQ3 at `0x504708` after reception. Enabling the existing MBUSTIM
clock in its product configuration allows an organic ACK and D2 version reply:
`V 05.56\n25-01-02\nNPE-3\n(c) NMP.`. The inherited 423.1Hz timing is not a
new measurement of NPE-3 silicon. No firmware state or service reply is injected.

`noki6210_mbus_service_client.lua` observes TX echoes through a read-only
controller tap and acknowledges the received sequence through `MBUS_RX`.
The MCU's ACK receive parser is asymmetric: `0x4c861e` recognizes type7f,
`0x4c8634` disables RX after byte5, and `0x4c8644` compares that sequence
against the outstanding one. It does not consume the external checksum byte.
The checker requires this rejection explicitly, rather than claiming all six
ACK bytes were accepted. One request ACK and one D2 reply are observed, with
no retransmission through24s; without the host ACK the D2 repeats three times.
All four NVRAM files (flash, SIM, network, CCONT) match a fresh no-query24s
control byte-for-byte. This establishes read-only version access, not identity
provisioning, arbitrary memory acquisition or native DSP completion.

`verify-6210-mbus-service` creates fresh client/control runs, pins the own MCU
SHA1 and version text, checks query ingress plus response/ACK behavior, and
compares complete NVRAM file names and contents. Existing MBUS, default and
coherent-frontier gates pass with the clock-enabled build.

Driver TX logging is capped and can exhaust before20s. Absence from that log
is not absence of traffic; the service fixture uses its independent bounded
MMIO observation. Fresh cross-ROM repeated-byte fixtures pass at1.1ms on
NSE-8 v6.00/v5.01 (`tmp/nse8-mbus-1100us-v600` and
`tmp/nse8-mbus-1100us-v501`); the NPE-3 repeated-byte gate also passes.

### NPE-3 service catalogue boundary

Read-only observation of the version query resolves the source getter
`0x4b0476` (reads pointer `0x286818` to own version text `0x2867f8`), called
indirectly at `0x49fe92`, with return `0x49fe94`. The dispatcher beginning
`0x49fda0` uses message byte8 as a function-table index, rejects indices
at least `0x67` and null functions, and decodes arguments from byte10's
selector before the indirect call. Its literal at `0x4a013c` selects table
`0x255da0`: 103 slots, 94 non-null; slot0 is getter pointer `0x4b0477`.
`tools/noki6210_service_catalogue.py` extracts this own-hash-pinned table.
These are internal slots, not established MBUS command numbers. Next work is
to classify the handlers and their wire mapping before trying further reads;
no arbitrary memory/DSP acquisition capability is established by this table.

The observed dispatcher message is the original query frame:
`1f0010d10005000100030001d8`. Thus byte8 selects slot0, byte9 selects string
return handling (3), and byte10 selects argument decoding (0); these offsets
are runtime-confirmed, not a borrowed command-name mapping.

Initial static classifications: slot1 (`0x4dbfea`) is a masked peripheral-byte
**writer**, while slot2 (`0x4dc060`) reads the corresponding masked byte.
Both split argument0 into an upper-byte register index and low-byte mask;
indices below `0xf4` address base `0x20000`, others base `0x40000` (literals
`0x4dc2a0/0x4dc2a4`). Slot2 is not arbitrary RAM or DSP-ROM access, and MMIO
reads may have side effects. Neither slot has been exercised as a probe.
Classify remaining handlers before choosing a read-only acquisition candidate.

Further bounded classifications (not exercised): slot`0x0e` at `0x5031c4`
decodes a24-bit destination, byte count and source bytes, then calls the
copy helper `0x506930`; this is a memory **write**, not a read candidate.
Slot`0x0d` at `0x503206` instead returns a decoded24-bit address or zero:
it permits addresses at most `0x1fffff` or at least `0xa00000`, rejecting
the MCU flash interval `0x200000..0x9fffff`. Its literal limit is `0x1fffff`
at `0x50328c`. Returning a pointer is not by itself a safe memory-read API:
dispatcher string/buffer response branches copy through the returned pointer
and subsequently call `0x3c2a68` on it (`0x49fef4..0x49fef6`). Allocator
ownership and reply-selector contracts need decoding before any probe.
Slot`0x18` (`0x426952`) writes a selected DSP/shared control cell and publishes
further control state; it is not a read-only DSP-ROM path. These classifications
do not establish an acquisition route to missing resident DSP routine`0x2c75`.

The allocator helper `0x3c2a68` checks a returned pointer against heap bounds
at `[0x100020+0x24]` and `[0x100020+8]` before examining block metadata
(`0x3c2a70..0x3c2a7c`). Static pointers outside the heap therefore need not
be allocations, but this does not make arbitrary in-heap pointers safe.

Slot`0x04` (`0x426d14`) clears2048 shared halfwords and resets DSP-related
control state: it is an initializer, not acquisition. Slot`0x0f`'s wrapper
`0x4ca9ba` calls `0x503258`, which locks around `0x3fec30`; that helper
copies from MCU cache base`0x15e8d8` and accepts only a nonzero extent whose
offset-plus-size is at most`0x9c4`. This does not address resident DSP code.
The full wrapper argument grammar/effects remain unqualified. Its paired
slot`0x10` calls `0x503228/0x3fe944` and must not be treated as a read.

Acquisition limit: software service access to this emulator can expose only
bytes already present in its MCU, uploads, cache or modeled shared RAM. It
cannot independently recover absent resident DSP ROM. A service transaction
that makes the missing DSP routine execute is still blocked by that same
missing routine; HLE-generated replies would not be independent evidence.
The catalogue remains useful for mapping hardware and eventual real-phone
capture, but is not by itself a pure-software source of new mask-ROM data.

## Timer and remaining uncertainty

The controller uses the physical 9,600-baud rate with a ten-bit character time
(approximately 1.042 ms) for byte completion. The public MADos interrupt map
independently identifies FIQ3 as `FIQ_MBUSTIM` at 423.1 Hz, distinct from the
FIQ2 receive/transmit event. Products with an independently exercised timer
contract arm one terminal event when firmware unmasks FIQ3; status writes do
not arm that event. The byte-level model does not implement the service-loader
bit path described below. The 3210 profiles retain the
established no-FIQ3 ordinary-boot behavior until their clock gate is identified.

M2BUS is a single-wire half-duplex bus, so a transmitted byte is also sampled
by the receiver. The controller now exposes each completed TX byte through its
RX holding state; NAM-2 consumes and compares that echo through its ordinary
FIQ2 handler before sending the next byte. Public protocol documentation also
specifies 3 ms of idle bus before an ordinary frame, 2.5 ms before an ACK and a
200 ms ACK timeout. Simultaneous byte drivers resolve through the open-drain
wired-AND rule. Status bit 6 is the sampled clock/idle line: a peer byte keeps
it low for one physical character time, preventing firmware from starting a
retry over an occupied wire. Before that state was modeled, the status register
always claimed idle and permitted avoidable retries over peer traffic. The
precise oscillator phase within a bit, differing-bit arbitration, framing
errors, overrun behavior and electrical timing remain unmodeled.
The lower service/test protocol behind task 7 is mapped separately; ordinary
boot provides no evidence that it is an always-present MBUS peer. A future
tool or peer must attach through the byte callbacks and may respond only to
organic transmitted frames.

NAM-2 v5.84 supplies the first organic startup use of this controller. Its
initializer at `0x2f7f90`, start routine at `0x2f7c24`, FIQ3 handler at
`0x2f7d2a`, and byte-event state machine at `0x2f7d86` establish the
FIQ3-timer/FIQ2-byte-completion split independently of the ROM4 firmware.
The shared controller model therefore transmits
`1f ff 00 d0 00 01 01 01 31` with a valid zero XOR over the frame. No peer is
inherited from another product: a trial using the superficially similar DSP-service D0 state-1/state-4
reply was consumed byte-for-byte but rejected by firmware. This closes the
controller behavior without conflating the physical terminal and DSP-service
protocols.

Public [Gammu/Gnokii Nokia protocol documentation](https://docs.gammu.org/protocol/nokia.html)
closes the wire-level application vocabulary. M2BUS uses terminal node `0x1d`,
requires a type-`0x7f` transport acknowledgement for normal frames, and defines
terminal startup request `1f 00 1d d0 00 01 04 <seq> <xor>` followed by phone
response `1f 1d 00 d0 00 01 05 <seq> <xor>`. NAM-2 attaches
`nokia_mbus_terminal_device`, which implements only this public wire grammar. It
waits the specified idle periods, derives ACK endpoints, sequence and XOR from
the received frame, gates transmission on the controller's one-byte holding
register, and restarts a pre-empted frame after the phone wins the single wire.
`make verify-2100-mbus` proves the ordered organic exchange: phone `D0/01`,
terminal ACK, terminal `D0/04`, phone `D0/05`, terminal ACK. No firmware
address, RAM state or sibling-handset timing appears in the peer.

The remaining hardware uncertainty is below that protocol acceptance point:
oscillator phase within a 423.1 Hz period, bit-level arbitration, electrical
timing and error reporting.

## Static service-loader bit path

The separately acquired `DCT3BT2.TIA` and `WD1BT2.TIA` bootstraps select their
serial base through bits 5:4 of the byte read at `20000`. Their four-entry
tables and source identities are maintained in
`hardware_atlas.md#service-loader-references`, not inferred from a phone name.
Selector 2 addresses status `20019` and receive data `2001a`, matching this
device's mapped window; other selectors use different addresses and are not
automatically additional MBUS mappings.

The receive helper waits for status bit 5 before reading base+4. The transmit
helper sends eight payload bits LSB-first: wait for bit 6 clear, write the
payload bit in status bit 7, then wait for bit 6 set. It finally reads base+4.
These byte-matched static consumers corroborate the bit-5 receive test but
invalidate treating bit 7 as universally counter-reset-only. They do not
identify pin direction, clock ownership, baud, character framing, counter
side effects or a product's selected controller. In particular, the current
busy/idle projection of bit 6 does not reproduce those individual transitions.
No bit timing, selector alias, bootloader execution or normal-handset promotion
is added on this evidence. The 2100 sleep/wake restoration question is also
unaffected.
